# GLM Radar 首版设计

日期：2026-08-20  
状态：待用户复核  
产品名称：GLM Radar｜GLM 开源雷达  
副标题：追踪框架支持、修复进展与能力边界

## 1. 背景与目标

GLM Radar 是面向 GLM 系列模型使用者和框架维护者的中文信息门户。首版聚焦四个主流开源框架，自动采集与 GLM 相关的 GitHub Issue 和 Pull Request，生成可追溯的中文站内日报，并提供按硬件与使用场景分类的框架能力查询。

首版必须具备真实、持续的数据采集能力，而不是静态演示。所有自动归纳结果都保留原始 GitHub 证据链接、数据时间和摘要生成时间，避免 AI 摘要替代事实来源。

### 1.1 首版目标

- 每日增量采集四个框架仓库中与 GLM 相关的 Issue 和 PR。
- 使用 OpenAI API 生成结构化中文摘要与分类。
- 生成可按日期查询的站内日报。
- 提供可搜索、可组合筛选的 Issue / PR 动态库。
- 提供按 NPU / GPU、训练 / 推理 / RL 分类的框架能力矩阵。
- 提供单管理员后台，用于管理仓库、关键词、同步任务和能力条目。
- 在单个外部服务异常时继续提供已有数据，并明确显示数据新鲜度。

### 1.2 首版不包含

- 普通用户注册、登录和个人收藏。
- 邮件、企业微信、飞书或 Slack 推送。
- 社区投稿、评论和公开编辑。
- 复杂趋势图表、排行榜或社区热度评分。
- 自动发布未经人工确认的能力矩阵变更。

## 2. 数据源范围

首版只监控以下仓库：

| 框架 | GitHub 仓库 | 默认启用 |
| --- | --- | --- |
| LLaMA-Factory | `hiyouga/LlamaFactory` | 是 |
| MindSpeed-LLM | `Ascend/MindSpeed-LLM` | 是 |
| verl | `volcengine/verl` | 是 |
| vLLM | `vllm-project/vllm` | 是 |

管理员可以在后台新增、停用或修改仓库。每个仓库配置独立的关键词、采集游标和同步状态。

默认关键词集合覆盖 `GLM`、`ChatGLM`、`GLM-4` 及其大小写、分隔符和常见版本写法。管理员可编辑全局关键词，也可为单个仓库添加专属关键词。关键词命中只决定是否进入候选集合；最终分类由结构化解析与 AI 摘要共同完成。

## 3. 用户与权限

### 3.1 公开访客

无需登录即可访问首页、日报、动态库、详情页和能力矩阵。公开接口只提供读取能力，并对高频请求进行基础限制。

### 3.2 管理员

首版只有一个管理员角色。管理员通过部署时设置的口令登录，可修改配置、触发同步、审核能力候选和编辑能力条目。

管理员口令不写入数据库。登录接口以恒定时间比较校验口令，成功后签发短期会话 Cookie。Cookie 必须设置 `HttpOnly`、`Secure` 和 `SameSite=Lax`，并由独立会话密钥签名。管理写操作必须校验会话并写入审计记录。

### 3.3 定时调度器

定时任务使用独立的 `CRON_SECRET` 调用服务端同步入口，不能复用管理员口令或会话。生产环境由私有 GitHub Actions 定时工作流在北京时间每天 08:30 调用；工作流中的站点地址和调度密钥使用 GitHub Actions Secrets 保存。后台可修改“日报统计日界线”和展示时区，定时工作流时间的改变需要同步修改工作流配置。

## 4. 信息架构

### 4.1 首页

首页是一份偏编辑化的“今日技术研究简报”，而不是高密度运维大屏。

首屏包含：

- 产品名称、定位说明和数据更新时间。
- 今日新增、已修复、待关注三个关键数字。
- 当日 AI 日报导语。
- 最值得关注的三个变化。

后续区域包含：

- 四个框架的最新动态概览。
- 新增支持、Bug 修复、未解决问题、值得关注四组日报内容。
- 能力矩阵的近期变更入口。

### 4.2 每日简报

- 默认展示最新一篇完整日报。
- 支持按日期访问历史日报。
- 日报分为新增支持、Bug 修复、未解决问题和值得关注四个板块。
- 每个条目展示框架、类型、状态、中文摘要、影响标签和原文链接。
- 当部分仓库同步失败时，页首显示明确的来源状态与缺失范围。

### 4.3 Issue / PR 动态库

- 支持标题、正文摘要和编号搜索。
- 支持组合筛选：框架、Issue / PR、开放 / 合并 / 关闭、GLM 型号、NPU / GPU、训练 / 推理 / RL、类别和严重程度。
- 默认按最后变化时间倒序排列。
- 筛选条件写入 URL 查询参数，便于复制和分享。
- 空结果页说明当前筛选条件，并允许一键清除部分或全部筛选。

### 4.4 条目详情页

- 展示原始标题、仓库、编号、作者、创建时间、更新时间和 GitHub 状态。
- 展示中文一句话摘要、详细摘要、影响范围、严重程度和分类标签。
- 展示状态变化时间线与关联 Issue / PR。
- 明确区分“GitHub 原始信息”和“AI 归纳”。
- 提供原始 GitHub 页面链接和摘要生成时间。

### 4.5 框架能力矩阵

矩阵以列表为主，支持以下筛选维度：

- 硬件：NPU、GPU。
- 场景：训练、推理、RL。
- 框架：LLaMA-Factory、MindSpeed-LLM、verl、vLLM，以及后台新增框架。
- GLM 型号。
- 支持状态：已支持、部分支持、实验性、计划中、不支持、未知。

每个能力条目包含能力名称、框架、GLM 型号、硬件、场景、支持状态、最低框架版本、限制条件、最近验证日期和一个或多个证据链接。移动端使用可展开列表，桌面端使用横向可读表格。

### 4.6 管理后台

后台包含四个工作区：

1. 仓库与关键词：新增、编辑、启停仓库，管理关键词和采集游标。
2. 同步运行：查看每次运行的开始时间、结束时间、分仓库结果、错误和重试状态；支持手动补采。
3. 能力候选：审核从 PR、Issue 或文档变化中自动发现的能力变更建议。
4. 能力维护：直接新增、编辑、归档能力条目及证据链接。

## 5. 视觉与交互设计

整体采用受 Claude 产品气质启发的温暖、克制、编辑化风格，不复制其商标或专有图形。

- 背景使用暖米白，主文字使用深棕黑，强调色使用陶土橙，辅助色使用柔和灰褐。
- 大标题使用具有编辑感的衬线字体；正文、筛选控件和数据表格使用高可读无衬线字体。
- 主要依赖留白、细分隔线和轻微圆角组织层级，避免密集卡片、霓虹色和传统监控大屏效果。
- 状态不能只依赖颜色表达，同时提供文本、图标或形状差异。
- 动效只用于筛选切换、内容展开、提交反馈和加载状态，并尊重 `prefers-reduced-motion`。
- 桌面导航采用顶部主导航；窄屏使用紧凑菜单，核心搜索与最新日报入口保持可见。

## 6. 系统架构

系统采用 Sites 能力路径，应用、服务端接口和管理后台位于同一个可部署项目中。

### 6.1 组件边界

- 页面层：负责公开页面与管理界面渲染，不直接访问外部 API。
- 查询服务：封装公开搜索、筛选、日报和能力矩阵读取。
- GitHub 采集器：按仓库和游标拉取变化，规范化 Issue / PR 数据。
- 关键词与相关性过滤器：先做确定性匹配，再生成待摘要记录。
- OpenAI 摘要器：输出符合 JSON Schema 的中文摘要与分类。
- 日报生成器：从指定日期的状态变化构建日报。
- 能力候选生成器：从重要 PR、Issue 和文档记录生成待审核候选。
- 管理服务：处理配置变更、审核、手动同步和审计。
- D1 数据访问层：集中管理数据库查询，页面和业务服务不直接读取绑定。

### 6.2 数据流

1. 调度器向受保护的每日任务入口发送请求。
2. 任务读取启用仓库及各自游标。
3. GitHub 采集器获取自上次成功同步后新建或更新的 Issue / PR。
4. 系统以 GitHub `node_id` 为外部唯一标识进行幂等写入，并记录状态变化。
5. 关键词过滤器筛出与 GLM 相关的记录。
6. 当原始内容哈希或关键状态改变时，记录进入摘要队列。
7. OpenAI 摘要器生成结构化结果并进行运行时 Schema 校验。
8. 日报生成器按北京时间日界线汇总当天变化，生成或更新当天唯一日报。
9. 能力候选生成器创建待审核项，不直接修改公开能力矩阵。
10. 所有仓库处理结束后记录本次同步结果并更新成功仓库的游标。

### 6.3 外部服务

- GitHub REST API：获取公开仓库 Issue / PR 及其状态变化。生产环境使用只读 Fine-grained Personal Access Token，以获得稳定限额。
- OpenAI Responses API：使用结构化输出生成中文摘要和标签。请求设置 `store: false`，只向模型发送完成摘要所需的公开 GitHub 内容。
- GitHub Actions：提供每日定时触发。定时工作流只调用站点任务入口，不直接写数据库。

## 7. 数据模型

### 7.1 `repositories`

保存框架名称、仓库全名、启用状态、专属关键词、采集游标、最后成功同步时间和创建/更新时间。

### 7.2 `github_items`

保存 GitHub `node_id`、仓库、编号、Issue / PR 类型、标题、正文、作者、状态、标签、原文链接、创建/更新时间、合并时间、内容哈希和首次/最后采集时间。`node_id` 唯一。

### 7.3 `item_events`

保存条目的状态变化事件，包括事件类型、旧值、新值、GitHub 时间和采集时间，用于详情时间线和日报归因。

### 7.4 `item_summaries`

保存一句话摘要、详细摘要、GLM 型号数组、硬件数组、场景数组、类别、严重程度、影响范围、建议关注级别、来源内容哈希、模型名称、提示词版本和生成时间。每个条目只有一个当前摘要，旧摘要可作为审计版本保留。

### 7.5 `daily_reports`

以北京时间日期为唯一键，保存日报导语、分组后的条目引用、来源同步完整度、生成状态、模型与提示词版本、首次生成时间和最后更新时间。

### 7.6 `capability_entries`

保存框架、GLM 型号、硬件、场景、能力名称、支持状态、最低版本、限制条件、验证日期、发布状态和创建/更新时间。

### 7.7 `capability_evidence`

保存能力条目的证据类型、URL、标题、来源日期和备注。一个能力条目可关联多个证据。

### 7.8 `capability_candidates`

保存自动发现的建议变更、来源条目、AI 理由、目标能力条目、审核状态、审核人标识和审核时间。

### 7.9 `sync_runs` 与 `sync_run_sources`

分别保存整次同步与单仓库处理结果，包括状态、计数、耗时、错误类别、可重试标记和触发方式。

### 7.10 `audit_logs` 与 `login_attempts`

保存管理员写操作审计和登录频率限制所需的最小信息。不保存管理员明文口令。

## 8. 摘要与分类契约

OpenAI 响应必须通过严格 JSON Schema 校验。核心字段如下：

- `headline_zh`：不超过 40 个汉字的一句话摘要。
- `summary_zh`：事实优先的中文详细摘要。
- `models`：识别出的 GLM 型号数组。
- `hardware`：`GPU`、`NPU`、`CPU` 或 `UNKNOWN` 的数组。
- `scenarios`：`TRAINING`、`INFERENCE`、`RL`、`EVALUATION`、`OTHER` 的数组。
- `category`：`NEW_SUPPORT`、`BUG`、`FIX`、`PERFORMANCE`、`DOCS`、`COMPATIBILITY`、`OTHER`。
- `severity`：`CRITICAL`、`HIGH`、`MEDIUM`、`LOW`、`INFO`。
- `impact_scope_zh`：影响范围说明。
- `attention`：`IMMEDIATE`、`WATCH`、`ROUTINE`。
- `capability_candidate`：是否可能影响能力矩阵。
- `evidence`：仅包含输入内容中可定位的事实依据，不生成新 URL。

提示词要求模型明确区分已确认事实、作者推测和 AI 推断。Schema 校验失败或模型拒答时，本次摘要标为失败，不覆盖已有成功摘要。

## 9. API 边界

公开读取接口：

- `GET /api/reports/latest`
- `GET /api/reports/:date`
- `GET /api/items`
- `GET /api/items/:repository/:number`
- `GET /api/capabilities`
- `GET /api/meta/status`

管理员接口：

- `POST /api/admin/login`
- `POST /api/admin/logout`
- `GET/POST/PATCH /api/admin/repositories`
- `GET/PATCH /api/admin/settings`
- `GET /api/admin/sync-runs`
- `POST /api/admin/sync`
- `GET/PATCH /api/admin/capability-candidates`
- `GET/POST/PATCH /api/admin/capabilities`

调度接口：

- `POST /api/jobs/daily-sync`

公开列表接口使用游标分页并限制最大页大小。所有写接口验证输入 Schema。管理员与调度接口分别使用会话校验和 Bearer 密钥校验。

## 10. 幂等性、失败与恢复

- 同步以仓库为隔离单元；单个仓库失败不阻塞其他仓库。
- 只有仓库完整处理成功后才推进该仓库游标。
- GitHub 数据以 `node_id` 幂等写入；状态事件使用条目、事件类型、事件时间和值哈希去重。
- 每个日期只有一篇日报，重复运行更新同一条记录。
- 原始内容哈希与摘要来源哈希一致时不重复调用 OpenAI。
- GitHub 限流时遵守 `retry-after` 或 `x-ratelimit-reset`，不进行紧密重试。
- OpenAI 临时失败采用有限指数退避；达到上限后保留失败状态，允许后续任务或管理员重试。
- 摘要失败不阻止原始记录公开，但页面明确标记“摘要待生成”。
- 日报生成前计算四个仓库的同步完整度；不完整时显示缺失来源，不沿用旧日报冒充今日数据。
- 公开页面在外部服务不可用时继续读取 D1 中的最近成功数据。

## 11. 性能与成本控制

- GitHub 采用增量请求和条件请求，避免每次全量扫描。
- 只对关键词命中的新记录和发生实质变化的记录调用 OpenAI。
- 列表页读取规范化字段和摘要，不加载大段原始正文。
- 常用筛选字段建立组合索引，包括仓库、类型、状态、更新时间、类别、严重程度和日期。
- 日报预生成，不在访客请求过程中实时调用外部服务。
- 首页和公开元数据接口使用短时缓存，并允许在后台数据更新后失效。

## 12. 可访问性与响应式要求

- 所有交互元素支持键盘操作并具有清晰焦点状态。
- 表单控件具有可见标签和可读错误信息。
- 状态同时使用文字与颜色，不以颜色作为唯一含义。
- 正文、次要文字和状态标签满足可读对比度。
- 桌面能力矩阵使用表格语义；移动端转换为可展开的定义列表。
- 动画尊重减少动态效果的系统偏好。

## 13. 测试与验收

### 13.1 自动测试

- 关键词规范化与相关性过滤单元测试。
- GitHub Issue / PR 规范化与幂等更新测试。
- 状态事件去重测试。
- OpenAI JSON Schema 合约测试，使用固定响应替身，不在测试中调用真实 API。
- 日报分组、日期边界和重复生成测试。
- 能力候选审核与公开矩阵发布测试。
- 管理员登录、会话过期、写接口拒绝和登录限流测试。
- 单仓库失败、GitHub 限流、OpenAI 失败和部分日报的集成测试。
- 搜索、组合筛选、游标分页和空结果测试。

### 13.2 首版验收

- 四个仓库均可完成真实增量采集。
- 连续运行两次不会产生重复条目、事件或日报。
- 结构化摘要字段完整，失败记录可以安全重试。
- 首页展示最新日报、重点变化和真实数据时间。
- 动态库支持全部约定维度的组合筛选。
- 能力矩阵能按硬件、场景和框架查询，并展示证据。
- 管理员可以新增仓库、修改关键词、手动采集、查看运行结果并审核能力候选。
- 在 GitHub 或 OpenAI 单独故障时，公开门户仍能展示已有数据与准确的同步状态。
- 站点可在桌面、平板和手机上使用，核心流程支持键盘完成。

## 14. 部署配置

运行时需要以下服务端密钥：

- `GITHUB_TOKEN`：只读 GitHub Fine-grained PAT。
- `OPENAI_API_KEY`：OpenAI 项目 API Key。
- `ADMIN_PASSWORD`：管理员口令。
- `SESSION_SECRET`：会话签名密钥。
- `CRON_SECRET`：定时任务调用密钥。

D1 作为唯一持久化数据库。首版不需要对象存储。数据库变更使用版本化迁移，部署前必须验证迁移和生产构建。
