# GLM Radar 历史同步与增量日报设计

## 目标

“全部动态”保存并展示四个已配置仓库中所有与 GLM 相关的 Issue / PR 历史记录；“日报”只展示北京时间当天被系统检测为新增或发生变化的记录。日报条目只显示标题、类型与编号、当前状态，并按重要性排序。

## 数据范围

- 完整集合：历史回填结果与后续每日增量的并集，按 GitHub `node_id` 去重，以较新的 `updated_at` 覆盖旧版本。
- 当日增量：某个北京时间自然日内首次采集到，或内容、标签、状态发生变化的相关 Issue / PR。
- 一天内重复执行同步时，当日日报对每次执行的增量取并集，不覆盖当天较早批次。
- AI 摘要不是进入完整集合或日报的前置条件。预算不足的记录仍保存标题、状态和上游元数据，摘要进入待处理队列。

## 历史回填

每个仓库增加可配置的 `historyStartAt`，首次真实数据部署时从该时间开始分页采集。回填不能依赖单次 GitHub Actions 在 20 分钟内完成，因此在 `manifest.json` 中为每个仓库保存回填状态：

- `pending`：尚未开始；
- `running`：已经开始但仍有后续分页；
- `complete`：已经追平日常增量游标。

每次任务最多处理配置限定的页数。成功写入并校验数据后才推进回填游标；失败时保留上一次已发布游标，下次继续。回填期间日常增量游标独立推进，避免遗漏新动态。

GitHub Issues API 的 Issue 列表包含 PR 包装项；采集器继续对 PR 读取完整状态。相关性筛选发生在写入之前，页面不会保存与 GLM 无关的仓库全集。

## 日报生成

同步开始时读取当天已有日报，取出已有 `itemIds`。本次完成标准化并确认有变化的记录形成 `deltaItems`，与已有 ID 合并去重后从完整集合中解析最新记录，再生成当日日报。

排序键依次为：

1. `attention`：`IMMEDIATE`、`WATCH`、`ROUTINE`、无摘要；
2. `severity`：`CRITICAL`、`HIGH`、`MEDIUM`、`LOW`、`INFO`、无摘要；
3. `updatedAt` 降序；
4. `id` 升序，保证构建结果确定。

日报摘要只保留数量统计，不复述 Issue / PR 正文。页面中的日报列表每行只渲染标题、`Issue #编号` 或 `PR #编号`、状态。标题可以链接到已有站内详情页，但不在日报行中展示 AI 摘要、分类或影响说明。

## 页面行为

- `/activity/` 的“全部动态”读取完整集合，继续提供类型、状态、分类和仓库筛选。
- `/activity/` 顶部日报区域展示当天增量标题列表，并保留“查看往期日报”。
- `/reports/:date/` 使用同样的紧凑标题与状态列表。
- `/reports/` 继续按日期展示归档入口。
- 没有当天增量时显示“今日暂无新增或变化”，不把历史记录填充到日报。

## 数据一致性与恢复

- 日报只能引用完整集合中存在的 ID；数据验证拒绝悬空引用。
- 回填和日常增量都先写临时文件，完整校验后再由现有数据分支发布流程提交。
- GitHub 限流触发安全阈值时停止当前批次，不推进未完成的回填位置。
- 重复采集、任务重试和同一天多次运行必须保持幂等。

## 测试

- 历史回填跨多次运行续跑并最终完成，期间不遗漏日常新增记录。
- 同一条记录重复出现时只保留最新版本。
- 同一天两次同步产生的不同增量同时出现在日报中，相同 ID 只出现一次。
- 旧记录未变化时不进入当日日报。
- 日报重要性排序、无摘要降级排序和空日报均有确定结果。
- 页面只在日报区域输出标题、类型编号和状态，全部动态仍包含完整集合。
- 完整测试、静态类型检查、数据验证和 GitHub Pages 构建通过。

## 首版迁移

样例数据保留用于本地视觉验证，但正式 `data` 分支初始化时不把样例游标视为历史回填完成。首次部署创建四个仓库的回填状态，然后按批次逐步构建完整集合。OpenAI 每日条数与费用上限保持不变。
